# Catalog guide: adding and editing products

All product data lives in `content/` as plain text (YAML) files. The site is
rebuilt from these files on every deploy. Every change is checked first: a
mistake stops the build with a clear message instead of breaking a page.

```
content/
├─ categories.yaml           category tree (Bedding → Comforter sets …)
├─ brands.yaml               brands of the products (not the store)
├─ options/
│  ├─ color.yaml             shared colors: id, SKU code, EN/ES name, swatch
│  ├─ size.yaml              clothing sizes
│  └─ bed-size.yaml          bed sizes
├─ products/<slug>.yaml      one file per product
└─ images.manifest.json      generated by images:sync — don't edit by hand
photos/<slug>/               your original photos (on your computer only, not in git)
```

## Add a product

```bash
npm run product:new
```

It asks for the name, category, brand, colors/sizes and how the product is
sold, then creates `content/products/<slug>.yaml` as a **draft** with a new
id. Then:

1. Open the file and write the description (English, and Spanish when you can).
2. Put photos in `photos/<slug>/` (see **Photos** below) and run `npm run images:sync`.
3. Run `npm run dev` and look at it. Drafts are visible locally and on Vercel
   preview links, never on the live site.
4. Change `status: draft` to `status: active`, commit and push.

`npm run content:check` validates everything and lists warnings such as
missing Spanish text or products without photos.

## The product file

```yaml
id: p_0002 # never change; assigned by product:new
slug: luxury-7-piece-comforter-set # URL and photo folder name; must match the file name
status: active # active | draft | archived
brand: example-brand # optional; from content/brands.yaml
categories: [bedding/comforters] # first one is the main category
name:
  en: Luxury 7-Piece Comforter Set
  es: Juego de edredón de lujo de 7 piezas
description:
  en: |
    Text in English…
  es: |
    Texto en español…
skuPrefix: BED-CMF7
options:
  color: [navy, gray, white, burgundy] # from content/options/color.yaml
  bed-size: [queen, king] # from content/options/bed-size.yaml
variants: # exceptions only
  - match: { color: burgundy, bed-size: king }
    available: false
packaging: # optional; leave out for items sold individually
  unit: set # piece | pack | case | set | dozen
createdAt: 2026-10-02
```

### Variants and SKUs are generated for you

Every combination of the listed options becomes a variant: 4 colors × 2 sizes
= 8 variants. Each gets a SKU made of the prefix plus the option codes, like
`BED-CMF7-NVY-QN`. You only write **exceptions** under `variants:`:

```yaml
variants:
  - match: { color: white } # every white variant…
    available: false # …shows as "currently unavailable"
  - match: { color: navy, bed-size: queen } # exactly one variant…
    sku: "000123456" # …uses the POS SKU instead of the generated one
    barcode: "0123456789012"
```

To give a variant its own SKU or barcode, `match` must name every option, so
it points to exactly one variant.

### Options

- **Shared lists** (`content/options/*.yaml`): colors, clothing sizes and bed
  sizes. Define a value once (id, SKU code, English and Spanish name, swatch
  color) and reuse it in any product. Add a new color there first, then use it.
- **One-off options** can be defined inside the product file. See
  `blackout-curtain-panels.yaml` (panel size) and `all-purpose-cleaner-32oz.yaml`
  (scent).
- A product can have up to 3 options. A product with no options (most
  perfumes) has a single variant whose SKU is the `skuPrefix`.

### Packaging

Leave `packaging` out for items sold one at a time. For packs and cases:

```yaml
packaging:
  unit: case
  unitsPerPack: 12 # "Case of 12"
  quantityStep: 1 # optional: order in multiples of this
```

The wholesale minimum is an **order total**, set in
`src/lib/config/site.ts`, not per product.

### Status

| Status | On the live site | On dev / preview links |
|---|---|---|
| `draft` | hidden | shown |
| `active` | shown | shown |
| `archived` | removed from listings; its link will redirect to its category (Phase 3) | same |

A product marked `active` can't contain the word `TODO`, so a half-written
description can't go live by accident.

## Photos

Put the original photos in `photos/<product-slug>/` and name them after the
option value they show:

| File name | Shown for |
|---|---|
| `navy-1.jpg`, `navy-2.jpg` | the navy variants (1, 2 = order) |
| `navy-queen-1.jpg` | navy + queen only |
| `main-1.jpg` | every variant, shown first |
| `detail-1.jpg`, `lifestyle-1.jpg`, `pack-1.jpg`, `back-1.jpg` | every variant, after the color photos |

Then run:

```bash
npm run images:sync
```

It resizes photos (max 2000 px), fixes rotation, converts them to JPEG,
makes a small blurred preview, and updates `content/images.manifest.json`.
Photos that haven't changed are skipped. Deleting a photo from the folder
and re-running removes it from the site. If a file name doesn't match any
option, `content:check` warns you.

**Where photos are stored:** if `CLOUDINARY_URL` is set in `.env.local`,
photos upload to Cloudinary. Otherwise they're saved in `public/catalog/` and
committed with the site, which is fine to start with. Switch to Cloudinary
before the catalog gets large, then re-run `images:sync`. Commit
`content/images.manifest.json` either way.

**Photo tips:** use the same background and lighting for every product,
portrait 4:5 framing, at least 2000 px on the long side, one front photo per
color, plus detail and packaging shots.

## Categories and brands

- `content/categories.yaml`: add or rename categories. The `id` path (e.g.
  `bedding/comforters`) is used in product files and URLs. Changing names is
  safe; changing ids changes URLs.
- `content/brands.yaml`: add each brand once, then reference it with `brand:`
  in product files.
